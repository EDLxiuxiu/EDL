# 演示与答辩提纲

## 约八分钟演示

1. 首页说明这是虚构数据教学模拟，选择 MySQL 持久化模式。展示数据版本及规则参数，创建原始 20 人运行。
2. 单独执行第一批，展示 S01 按资格和校内排名录取，1-B 余额转入 3-B；继续完整执行剩余批次。
3. 展示 1、5、8、2 的分批人数，总录取 16，未录取 4，4-D 剩余 1。打开结转，检查四条细来源。
4. 在 3-C 展示最低分 650、末位 S16 的 675 分、志愿 2、同分序号 1。解释最低分不能代替末位。
5. 查询 S11 或 S12，说明同梯度志愿优先造成第三批落选。首页分别创建对照 A、B，保持其他输入不变完整执行，展示新去向及 S13 被挤出的结果。
6. 展示 S18 的 600 与 S20 的 599；说明控制线等号允许，低一分即使有余额也不录取。
7. 展示已经保存的 15 万人运行及原始实验报告，查询固定六类考生，按高中、初中、批次、计划筛选并导出。不要现场为展示重复导入全部数据。
8. 展示完整核对、最近检查点及优化对照报告，说明未清缓存、重复次数和统计口径。实际报告尚未 verified 时明确说明待验收。

## 核心问题

**为什么不能按总分对每个人依次试完所有志愿？** 这样会让同梯度高分第二志愿抢在低分第一志愿之前，违背课程志愿轮次优先。代码的循环顺序必须是梯度、志愿轮次、当前轮考生。

**同分序号什么时候起作用？** 只在同梯度、同志愿轮次、竞争同一计划时比较；更靠前的志愿轮次先执行。675 分的 S17 第一志愿可以先于同分序号更小但第二志愿才到 C 的考生录取。

**为什么第二批保留生源初中？** 指标属于“高中加初中”子计划，某初中用完不能使用另一初中的剩余额度。余额只在第二批结束后转到本校第三批，不能批内挪用。

**为什么最低录取分不一定是末位分？** 按志愿轮次投档可能先录低分第一志愿、后录高分第二志愿。3-C 先录 650 分 S15，后录 675 分 S16，最低分与实际末位是不同统计。

**怎样避免重复结转？** 每次计算基于上一已提交检查点；提交时条件更新预期批次，只有一次成功。检查点、余额、考生状态与流水在同一事务提交。完成批次不能原地再执行。

**冗余为什么不会与明细各说各话？** 冗余不是多个地方各自修改的独立事实。每批从状态一次生成全部投影，同事务保存，audit 再从快照和检查点独立重建并全量比较。数据库 CHECK 和唯一键补充约束。

**为什么使用批次边界，而不是每次考生判断写一次数据库？** 逐判断往返会放大网络及事务开销。批内实时更新内存余额与录取集合，批末集中写库；界面进度反映已提交状态，崩溃后重算尚未提交的一批。

**优化了什么，有多少收益？** 已实现第一批按学校分组、后三批排序复用，以及按考生存储过程和按计划存储统计。业务一致性有本地规模证据；MySQL 收益必须引用新 query_comparison.json 的真实三轮中位数，不能凭结构或模拟连接耗时推算。

**历史报告的 SHA 与当前源码不同怎么办？** 报告对应原实验版本；用 Git 30ebf70 在另一目录复现。当前新报告记录新源码摘要。不能修改旧 SHA 或覆盖实验目录。

**为什么不把全部输入再拆成新主库六张可变表？** 历史规模库已经有规范化输入表。主系统为了保证版本整体一致，采用不可变输入聚合，并将查询频繁的结果结构化；代价是版本和投影占更多空间。报告同时给出逻辑实体与物理存储关系。
