# 部署与使用说明

## 当前项目启动

在项目根目录 PowerShell 执行。保留现有 MySQL 账号和密码；默认命令在本机用 getpass 输入，密码不会回显。

```powershell
.\.venv\Scripts\python.exe -B .\manage.py init-db
.\.venv\Scripts\python.exe -B .\manage.py web
```

第一条用既有 root 初始化独立主库及授权，第二条用 admission_app 启动界面。浏览器打开 http://127.0.0.1:5000 。端口占用时使用 `web --port 5001`。停止服务在原终端按 Ctrl+C；持久运行可在下次启动继续查看。

不需要数据库的演示：

```powershell
.\.venv\Scripts\python.exe -B .\manage.py web --demo
```

内存演示默认装入 20 人输入。界面明确标注存储模式，重启后丢失；它不能作为真实 MySQL 验收或性能证据。

## 新机器环境

安装 CPython 3.14 与 MySQL Community Server 8.4，创建虚拟环境并安装依赖：

```powershell
py -3.14 -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
```

MySQL 需监听 127.0.0.1:3306，支持 InnoDB、JSON、CHECK 约束和 utf8mb4。先使用本机 root 客户端创建 `admission_app`@`127.0.0.1` 应用账号并设置本机密码，再运行 init-db 授权。账号若已存在，不重设密码。不要将真实密码放入 SQL、Git 或 README。schema_app.sql 包含建库、建表和 GRANT，不负责静默创建或更换账号密码。

主系统创建六张表；原样例的 schema.sql、seed_sample.sql、schema_runs.sql 和独立规模库 schema_scale.sql 用于历史实验复现，与主系统分开。全新机器仅演示主系统时，不必先执行历史实验。

默认主系统本机地址、端口、账号及数据库见 config.example.json。需要时复制为被 Git 忽略的 config.local.json，再修改非密码字段；主系统仍强制只写本机 admissionsim_app，避免误写历史库。Web 端口由命令行配置，依赖版本见 requirements.txt。不对公网开放这个课程开发服务器。

## 操作流程

1. 在首页创建原始 20 人样例，或导入已有 data.json；生成器也可按固定种子生成 20 至 150000 人。
2. 点击数据版本，查看或编辑学校、计划、资格、考生和志愿。输入校验失败不会保存新版本。保存成功得到独立版本，原版本仍保留。
3. 首页选择数据版本，填写年度、控制线、第一梯度和间隔，创建独立运行。
4. 在运行页选择执行下一批或完成剩余全部批次。进度条显示已成功提交的批次，文本显示计算或保存阶段。
5. 查看考生名单与处理过程、计划统计、最低分与末位、各校及各初中统计、分数分布和结转流水。
6. 用编号筛选，或点击高中、初中、计划直接查看对应名单。导出当前筛选 CSV、全运行五维统计 CSV 或完整输入 JSON。
7. 用完整一致性核对检查全部冗余和检查点。不要只凭页面汇总推断全部录取正确。

计划或学校编号只允许字母数字下划线，计划编号使用批次与学校等字段以连字符组合。考生的各批志愿用空格分隔，不能重复。资格编辑器以高中为键，保存合格考生到校内排名的映射。删除学校或考生时仍须满足引用完整性，否则拒绝新版本。

## 统一命令与真实验收

直接导入既有 15 万人数据，命令输出数据版本 UUID：

```powershell
.\.venv\Scripts\python.exe -B .\manage.py import .\experiments\scale_150000\data.json --label "15万人原始输入"
.\.venv\Scripts\python.exe -B .\manage.py run --dataset-id <上一步输出的UUID>
.\.venv\Scripts\python.exe -B .\manage.py check <主系统运行UUID>
```

如果需要完整的新主库验收与查询对照，优先只运行以下集成命令，避免先重复手动导入：

```powershell
.\.venv\Scripts\python.exe -B .\manage.py accept --out .\experiments\app_mysql_acceptance_v1
```

它在新主库创建新的样例及规模输入版本、运行和检查点，使用历史库只读查询作对照。输出目录拒绝覆盖。一次应用密码输入覆盖该进程的全部步骤。报告保存每阶段耗时、固定 UUID、全量核对与查询原始样本。schema、源码以及已有历史库必须准备好；历史大 JSON 在新机器上需按相同种子生成并通过原 manifest 摘要核对后才能执行优化对照。

提交或连接异常时先查看目录里的 acceptance.json。修复环境后，可恢复同一目录及固定 UUID：

```powershell
.\.venv\Scripts\python.exe -B .\manage.py accept --out .\experiments\app_mysql_acceptance_v1 --resume
```

恢复先查回是否已提交，不删除或盲目重建。源码变化时拒绝自动恢复旧验收。查询子目录若已有失败报告，应保留证据，并使用 benchmark 的新目录单独补测，不覆盖失败记录。

只补旧全运行计划统计基准，或对已完成的新运行补测：

```powershell
.\.venv\Scripts\python.exe -B .\manage.py benchmark --out .\experiments\legacy_plan_query_v1
.\.venv\Scripts\python.exe -B .\manage.py benchmark --run-id <主系统15万人UUID> --out .\experiments\query_compare_v2
```

## 测试与历史复现

```powershell
.\.venv\Scripts\python.exe -B -m unittest -v test_admissions test_input_validation tests.test_system
.\.venv\Scripts\python.exe -B .\manage.py verify-local --out .\experiments\app_local_new_version
```

后者只运行新的本地正确性验收，不连接 MySQL；无需为文档更新重复执行规模核对。

`tests/test_mysql.py` 是显式启用的真实主库故障验收，默认跳过。只有本人确认允许读取本机凭据文件时，才在本机终端临时设置环境变量运行：

```powershell
$env:ADMISSION_MYSQL_TEST_CREDENTIAL_FILE = 'password.txt'
$env:ADMISSION_MYSQL_TEST_OUT = 'experiments/app_mysql_fault_new_version'
.\.venv\Scripts\python.exe -B -m unittest -v tests.test_mysql
Remove-Item Env:ADMISSION_MYSQL_TEST_CREDENTIAL_FILE
Remove-Item Env:ADMISSION_MYSQL_TEST_OUT
```

凭据文件不会被输出或纳入报告；测试只在新主库创建新样例，真实注入提交前异常并验证回滚、新连接恢复及数据库约束。不覆盖已有测试目录。

`tools/build_report.py` 是交付材料构建工具，不属于业务运行入口；需要 python-docx 和 Pillow。生成 Word 后须使用本机 Word 或 LibreOffice 渲染并检查所有页面。主系统运行只需要 requirements.txt 中的两项依赖。

当前三个核心算法文件已补参数和分组排序优化，旧实验工具按 SHA 检查时可能合理地拒绝新源码。旧实验准确复现应使用独立目录的原版本：

```powershell
git archive 30ebf707c2a7180d3ede588812458da8e4d11ff5 --output=legacy-30ebf70.zip
```

将压缩包解压到另一个目录，并恢复被忽略的大 JSON。不要在当前目录用 git reset 覆盖新工作，也不要修改旧报告的 SHA。历史只读查询函数仍可复用，但历史保存或基准执行按对应版本复现。

本轮三次 MySQL 查询对照的报告目录分别附有 source_snapshot.zip 与 source_snapshot_manifest.json。归档中的每个源文件已逐字节匹配对应原报告的 SHA，包含当轮源码与依赖说明，不包含密码或大数据。需要复现中间迭代时，解压到另一个工作目录，并恢复同一结构的数据及历史报告；不要把中间快照直接覆盖最终主系统。源码快照是实验版本依据，不是另一个业务入口。

## 常见问题

数据库连接失败不能据此判断已提交记录不存在。检查本机 MySQL84 服务与该次错误日志，再按固定 UUID 查回。独立主库首次建表使用 DDL，MySQL DDL 会隐式提交；初始化采用 IF NOT EXISTS，发生错误后先查看已有表，不 DROP 或清空历史库。

页面重启后 CSRF 表单失效时刷新即可。执行进程退出时正在计算的批次不会作为已完成显示；重新启动后继续该运行。内存模式没有持久检查点。CSV 大规模导出维持一份只读快照，下载期间尽量不要长时间悬置连接。
